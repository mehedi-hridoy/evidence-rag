
# ADR-0020: Database IDs, Timestamps, and Duplicate Detection

- **Status:** Accepted
- **Date:** 2026-11-02

## Context

EvidenceRAG needs consistent primary keys, reliable timestamps, and database-level protection against duplicate document uploads.

These decisions affect the initial database schema and future application behavior.

## 1. Primary Key Strategy

### Options considered

- **BIGINT IDENTITY:** Compact, sequential identifiers generated by PostgreSQL. However, identifiers are database-dependent and expose approximate record counts.
- **UUIDv4:** Globally unique identifiers that can be generated independently, but their random ordering can reduce index locality.
- **UUIDv7:** Globally unique, time-ordered identifiers with better index locality than randomly distributed UUIDs.

### Decision

Use UUIDv7 as the primary key for collections and documents.

Generate identifiers inside PostgreSQL using `DEFAULT uuidv7()`.

### Reasons

- UUIDs can be used across distributed components without coordinating integer sequences.
- UUIDv7 provides time ordering, improving index locality compared with UUIDv4.
- Database-side generation provides one consistent mechanism for all insertion paths.

### Consequences

- UUIDs consume more storage than BIGINT identifiers.
- UUIDv7 exposes approximate creation time through its timestamp component.
- IDs are generated by PostgreSQL rather than application code.
- PostgreSQL 18 is required for the built-in `uuidv7()` function.

## 2. Timestamp Strategy

### Options considered

- **TIMESTAMP:** Stores a wall-clock date and time without timezone conversion.
- **TIMESTAMPTZ:** Represents an absolute instant and supports timezone-aware input and display conversion.

### Decision

Use `TIMESTAMPTZ` for database timestamps.

### Reasons

EvidenceRAG may operate across different timezones. Storing absolute instants avoids ambiguity when comparing and processing events across locations.

### Consequences

- PostgreSQL converts input timestamps to UTC internally.
- The original timezone identifier is not retained.
- Values are displayed according to the database session timezone.
- Applications must handle timezone presentation explicitly when required.

## 3. Duplicate Document Detection

### Options considered

- **Application-level check before insertion:** Query whether a document already exists before inserting it.
- **Database unique constraint:** Enforce uniqueness directly in PostgreSQL.

### Decision

Calculate SHA-256 over the raw uploaded file bytes and enforce:

`UNIQUE (collection_id, content_hash)`

### Reasons

- Prevents exact duplicate uploads within the same collection.
- Allows the same document to exist in different collections.
- Database-level uniqueness prevents concurrent uploads from bypassing duplicate checks.
- The composite unique index also supports queries filtering by `collection_id`.

### Consequences

- Only byte-identical files are detected as duplicates. Semantically identical files with different byte representations are not detected.
- PostgreSQL unique constraint violations are raised as `UniqueViolation` by psycopg.
- The API must translate duplicate document violations into HTTP 409 Conflict with error code `duplicate_document`.
- The unique constraint creates an index that also supports collection-based document lookups.

## 4. Collection Deletion Policy

### Options considered

- **ON DELETE CASCADE:** Automatically deletes documents when their collection is deleted.
- **ON DELETE RESTRICT:** Prevents collection deletion while documents reference it.

### Decision

Use `ON DELETE RESTRICT` for the documents-to-collections foreign key.

### Reasons

Documents contain user-provided source material. Automatically deleting all associated documents through a collection deletion could cause unintended data loss.

Explicit deletion provides better control over destructive operations.

### Consequences

- A collection cannot be deleted while it contains documents.
- The application must explicitly delete or otherwise handle its documents before deleting the collection.
- Collection deletion requires an additional application-level workflow.

## 5. Initial Schema Scope

The first migration creates:

- `collections`
- `documents`

It also enables the PostgreSQL `vector` extension.

The `active_build_id` column is intentionally excluded because the `index_builds` table does not exist yet. It will be introduced through a later migration.
